## 1. 双击 Markdown 文件

- [x] **操作**：退出 readit；在 Finder 中分别双击一个 `.md` 和一个 `.markdown` 文件，
  两个文件均包含相对图片及一个指向同目录另一 Markdown 文件的链接。
  **期望**：readit 启动并显示被双击文件；相对图片可见；标题/内容与磁盘一致；两种扩展名
  均由同一个应用关联，窗口不出现空白文档。

  **结果：通过。** 同目录与子目录的相对图片都正确显示。补充事实：`.md` 与 `.markdown`
  在 macOS 上映射到**同一个 UTI**（`net.daringfireball.markdown`），所以「两种扩展名归
  同一应用」是结构性成立的，不可能分裂。另：**安装 readit 不会自动顶掉既有默认程序**
  （macOS 的反劫持设计，本机原先归 Xcode），必须由用户显式指定——这是真实用户会遇到
  的第一道坎，`README` 已写明。

## 2. 第二次启动路由到既有窗口

- [x] **操作**：保持 readit 已打开文档 A；从 Finder 双击文档 B，随后再从终端以带文档 C
  参数的方式启动 readit。
  **期望**：系统中始终只有一个 readit 应用实例；既有窗口被显示并聚焦，B、C 依次进入
  该窗口的文档导航历史；后退/前进可回到 A、B、C 的正确内容。

  **结果：通过。** 终端侧用的是**直接调二进制**
  （`/Applications/readit.app/Contents/MacOS/readit-shell <path>`）而不是 `open -a`——
  后者由 LaunchServices 直接激活既有应用、根本不起第二个进程，测不到
  `tauri-plugin-single-instance`。

  **记录**：前进/后退的键位是 `Alt+←/→` 或 `Cmd+[`/`Cmd+]`，监听挂在**元素宿主上而不是
  window**（`navigate.ts:306`），而壳从不主动聚焦元素。

## 3. Cmd+F

- [x] **操作**：打开含多个相同词、且至少一个命中位于首屏之外的文档；按 `Cmd+F`，输入
  查询词，使用 Enter、Shift+Enter 和界面前后按钮，再按 Escape。
  **期望**：组件自带查找栏获得焦点；总数/当前序号正确；当前命中滚入视野；正向与反向
  循环一致；Escape 关闭查找栏且文档 DOM/内容未被破坏。

  **结果：先失败，修复后通过。** 首轮：Enter / Shift+Enter / 界面按钮都能移动当前命中，
  但**视口从不跟随**。根因是 `revealRange` 把内容面板同时当作滚动容器和视口矩形，而
  阅读模式下面板会撑满内容全高、根本不是滚动容器（实测 scrollHeight 16051 =
  clientHeight 16051，真正能滚的是 HTML：16051/768）——两个分支都不进。已改为从命中
  本身推导滚动容器（提交 `e24e580`），并补了两条浏览器断言（页面流 / 受限高度两种配置）。

## 4. 原子保存文件监听

- [x] **操作**：readit 打开文档后，用会采用"临时文件 + rename"方式保存的编辑器修改并
  保存该文档；再用普通原地写入方式保存一次。
  **期望**：两种保存方式都只触发有效刷新，readit 显示最新完整内容；不丢失监听、不读到
  半写入文件、不进入重复刷新循环。

  **结果：通过。** rename 之后 **inode 从 13541279 变为 13632136**（真的替换了 inode，
  盯 inode 而不是路径的实现会在这一步永久失聪），刷新正常；普通原地写入同样刷新；
  静置期 `readit-shell` 与 `WebContent` 的 CPU 三次采样都是 0.0%，无重复刷新循环。

  **一条已知边界（不影响本项判定）**：额外用一个人工的 600ms 半写入窗口（截断 →
  写前半段 → 停 0.6s → 写后半段）探测，readit **会短暂显示残缺内容**，写入完成后自行
  纠正。机制：Rust 侧是裸 `notify::recommended_watcher`（无 debouncer），沉降只靠前端
  `watch-reload.ts` 的 **80ms** 防抖，首末字节跨度超过它就可能读到中间态。这个竞态
  **一般情况下不可修**——POSIX 没有办法让读者知道一个不配合的写者写完了，原子保存
  存在的理由正是消除它。清单点名的两种方式都已通过，故本项判为通过。

## 6. 安装体积、冷启动与稳态内存

- [x] **操作**：用 release 配置生成并安装 `.app`/`.dmg`；记录安装包与展开后应用体积；重启
  系统或确保进程/缓存条件可说明后测至少 5 次冷启动；打开一份普通、无数学/高亮/Mermaid
  的文档，静置 60 秒后记录稳态常驻内存，另行记录四个大件同时渲染的压力场景。
  **期望**：报告分别列出体积、每次冷启动及中位数、普通文档稳态内存、压力场景内存；不得
  用既有 514 MB 压力读数冒充稳态，也不得在尚无预算裁决时自行宣称性能通过。

  **结果：数据齐备，未宣称"性能通过"**（预算尚无裁决，按清单要求不自行下结论）。

  | 项 | 值 |
  |---|---|
  | `readit_0.1.0_aarch64.dmg` | **7.7 MB** |
  | `readit.app` 展开后 | **18 MB** |
  | updater `.tar.gz` | 7.8 MB |
  | 冷启动 ×5（`plain.md`） | **1093**（最冷）／459／443／464／423 ms，**中位 459** |
  | 普通文档稳态（静置 60s） | **112.3 MB** |
  | 压力场景（静置 60s） | **172.4 MB** |

  **口径**：冷启动用 `CGWindowList` 轮询到主窗口出现为止（只读 owner 名与窗口尺寸，
  不需要屏幕录制权限），每次测量前确认 `readit-shell` 进程已真正退出；缓存条件为
  **进程未运行、未 reboot、未 purge**，故第 1 次单列。内存用 `footprint` 的
  phys_footprint（即 Activity Monitor 口径），按「启动前后 WebKit 进程集合求差」定位
  readit 自己的主进程 + GPU + Networking + WebContent 四个进程加总。

  ⚠️ **压力场景是三个大件不是四个。** 壳里没有模式切换入口，CodeMirror 用户根本
  够不着，四大件在壳内凑不齐——见台账 **D2-28**。172.4 MB 是数学 + 高亮 + Mermaid
  的读数，不能当作四大件。

### 本次发现的三个缺陷（全部已修并推送）

三个都在库层、Rust 层、happy-dom 层乃至 Playwright 层是绿的，只有真机能看见：

1. **语法高亮在出货应用里从未生效**（`29ac972`）。壳调 `createShikiHighlighter()` 不传
   `langs` → 空语言集 → `supports()` 恒 false → 每个围栏静默回落朴素 `<pre>`。接口层
   `loadHighlighter` 原本无形参，宿主根本没有办法把这件事做对。库层测试全绿是因为它们
   自己传 `langs`，壳层则完全没有覆盖 `main.ts` 的接线。
2. **Mermaid 长标签被节点框裁掉**（`b79d7cb`）。测量钉死 `line-height: normal`，而渲染
   继承 `.markdown-body` 的 1.5，低估约 30%。中文与英文都会。
3. **图层护栏被 `classDef` 绕过**（`8c94a93`）。`classDef` 编译成注入 SVG 的 `<style>`
   规则，而护栏只摘行内声明。标签在真 WKWebView 里被画到未变换的原点上——正是
   WebKit bug 23113 的症状。

外加第 3 项的查找滚动缺陷（`e24e580`），共四处修复。
