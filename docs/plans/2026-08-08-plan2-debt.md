# 计划二的在案债务

计划一收尾时的完整欠账清单。每一条都**具名、带出处、可核验**——与
`packages/core/test/known-mismatches.json` 同一原则：债务的价值在于它是一份可读的清单，
不是一个静音开关。

出处标注三种：**实测**（有命令与输出）、**评审实测**（评审自己跑的探针）、
**推断**（从测量泛化，未单独验证——这类在本项目里已经错过四次，看到就当它可疑）。

## 一、三条「自选广度」的承重声明

全分支评审点名的一类风险：**声明的广度由做声明的人自己选定**。这条分支上它已经
造成四次「完整集」被后一轮推翻（`<template>` → `+script` → `+col` → `col 其实位置敏感`）。
下面三条同源，且**尚未被任何更宽的测量检验过**。

> **2026-08-09 更新：三条里的第一条已经用更宽的测量检验过了，结果是被推翻。**
> D2-1 的「带 height 就发扩展形式」在七种 `height` 形态里错了四种。
> 这是这一节的论点第五次被自己的样本证实——**推断的广度由做推断的人选定时，
> 它倾向于错**。剩下 D2-2 / D2-3 两条仍未检验，性质完全相同。

### ~~D2-1 `imageStyle` 的三声明形式源自 n=1~~ —— ✅ 已还清（2026-08-09，实测）

- **位置**：`packages/core/src/rules/rawshape.ts` 的 `imageStyle`
- **原判断**：带 `height` 属性的图片发
  `style="max-width: 100%; height: auto; max-height: <N>px;"`，
  不带的发 `style="max-width: 100%;"`。整个夹具集里**只有一个**实例支持扩展形式
  （`real-world/mermaid` 的 `<img height="150">`），对 46 个朴素实例；
  代码里标了三处 UNVERIFIED，但它们**静默走 height 分支**。
- **怎么还的**：八个单目的语料（`github-only/image-height-*` +
  `image-width-and-height`），每个一个 `<img>` 形态，
  2026-08-09 对活 oracle 抓取（`contents` + `Accept: application/vnd.github.html`，
  自仓 ref `c764d959`）。

#### 实测结论：**推断是错的，四处于七。**

| `height` | 语料 | GitHub 发的 `style` |
|---|---|---|
| 无 | `image-height-none` | `max-width: 100%;` |
| `150` | `image-height-numeric` | `max-width: 100%; height: auto; max-height: 150px;` |
| `50`（且有 `width`） | `image-width-and-height` | `max-width: 100%; height: auto; max-height: 50px;` |
| `50%` | `image-height-percent` | `max-width: 100%;` ❌ 原分支发 `max-height: 50%px;` |
| `10em` | `image-height-css-unit` | `max-width: 100%;` ❌ 原分支发 `max-height: 10empx;` |
| `0` | `image-height-zero` | `max-width: 100%;` ❌ 原分支发 `max-height: 0px;` |
| `abc` | `image-height-junk` | `max-width: 100%;` ❌ 原分支发 `max-height: abcpx;` |

**真正的判据是「正整数像素」，不是「有 height 属性」，也不是「值是数字」**
——`height="0"` 走朴素分支，这一条谁都没预测到，它才是把判据钉死在「正」而非
「数值」上的那个证据。三处 UNVERIFIED 里，只有 `width`+`height` 那一处
碰巧猜对了（`width` 不干扰，判据只看 `height`）。

四处错误全部产出**语法非法的 CSS**（`50%px` / `10empx` / `abcpx`），
且都发在原生 HTML 文档里——正是评审判定它风险/行数比最高的理由。

**附带定论**：`image-height-markdown` 证实 Markdown 图片语法**无法表达 height**
（GitHub 既不支持 kramdown/Pandoc 的 `{height=150}`，也不支持 `=150x`），
所以扩展形式从 `decorate.ts` 那侧不可达，它无条件发朴素形式是对的——
这是求证的结果，不是假设。

#### 仍未测量（现在**失败朝安全侧**，且已在代码注释里具名）

带空白的高度、前导零（`"0150"`）、小数、负数、超过 2^53 的值。
这些一律走朴素分支：那是 46 实例的多数分支，且永不产出非法 CSS。
它仍然是一个猜测，只是猜向了实测占优的一侧。另注：hast 会重写属性本身
（`height="0150"` 序列化回 `height="150"`），这类文档在轮到 `style` 之前
就已经与 GitHub 分叉了——那是序列化器的问题，不是 `imageStyle` 的。

- **代价**：语料 60 → 68，SPEC §13.3 上限由 60 上修至 70（见该处的修订说明）。
  八个新文件**全部匹配 oracle**，台账未增加条目（仍 12 条），语料 48/60 → 56/68。
- **出处**：全分支评审（架构）、修复轮 3 评审；本轮为实测还清

## 四之二、计划二自身产生的债务

### ~~D2-17 第 2 级（DOMPurify）的允许名单从未对着 Phase A 的输出审过~~ —— ✅ 已还清（批次 8，真浏览器实测）

**来源：实测**（批次 5 修复轮 2，`browser/element/trusted-types.spec.ts:70-73` 有记录）。

#### 批次 8 怎么还的

把第 1 级那次「跑完整语料、`DOMParser` 解析出期望集合、逐元素逐属性 diff 到零差异」的

`Reflect.deleteProperty` 逼走第 1 级、WebKit 天然选中第 2 级，两个引擎共用同一个
DOMPurify、结果一致）。语料覆盖 frontmatter 表格、标题锚点+Octicon、GFM alert+第二个
Octicon、GFM 表格、任务列表、图片、两种 emoji、行内数学降级、围栏代码块的
clipboard 包装、脚注引用与回链、原始 HTML `<details>`。

**完整差集（不止批次 5 碰巧撞见的两个名字）**：`markdown-accessiblity-table`、
`math-renderer` 两个已知自定义元素被 unwrap（连内容一起保留、丢外层标签）；
新发现 `<g-emoji class="g-emoji" alias="...">`（emoji.ts 对 29 个自带 HTML 标记的

`rel="noopener noreferrer"` 不受影响。

修法：`set-html.ts` 的第 2 级 `purify.sanitize()` 补 `ADD_TAGS`/`ADD_ATTR`
（`markdown-accessiblity-table`/`math-renderer`/`g-emoji` + `target`/`alias`），
与第 1 级 `buildTier1Sanitizer()` 同一原则——在默认允许名单上做加法，不替换它。

**顺带发现并修复的第 1 级同源缺口**：`g-emoji` 在浏览器原生 Sanitizer（第 1 级）下
同样被剥掉（且更彻底——整个元素连文字内容一起消失，不是 unwrap），此前的批次 5
诊断没有覆盖到 unicode emoji 这条路径。已在 `EXTRA_ELEMENTS` 里补上，真机验证过
（Chromium 未删改前后对照）。这不是本条债务的原定范围（D2-17 明确说第 1 级已诊断
完毕），是同一次诊断方法论顺手带出的一个真实缺口，一并还了。

真机测试与 unit 测试（`set-html.test.ts`）均绿；XSS 负控面未被这次加法打开——
`ADD_TAGS`/`ADD_ATTR` 只是 DOMPurify 允许名单的加法，`<script>`/事件处理器属性/
`<iframe>`/`<object>` 不受影响（DOMPurify 源码里这些从不在默认 `ALLOWED_TAGS`/
`ALLOWED_ATTR` 里，`ADD_TAGS`/`ADD_ATTR` 不能绕开这一点）。

**来源：实测**（批次 5 修复轮 2，`browser/element/trusted-types.spec.ts:70-73` 有记录）。

批次 5 花了很大力气修第 1 级的一个缺陷：**浏览器原生 `Element.setHTML()` 的默认允许名单
比 Phase A 的输出更严格**，`<img>`/`<input>`/`<details>`/`id`/`class`/`data-*` 会在写入
真实 DOM 这一步被静默剥掉。修法是 `buildTier1Sanitizer()`——在浏览器默认配置上做加法，
加了 `EXTRA_ELEMENTS`（6 个）与 `EXTRA_ATTRIBUTES`（9 个）。

**第 2 级有同一个问题，而它从来没被审过。** `set-html.ts` 的第 2 级是
`purify.sanitize(html, { RETURN_TRUSTED_TYPE: true })`——**除此之外一个配置都没传**。
DOMPurify 的默认名单和 Phase A 的输出是否对得上，从未有人测过；批次 5 只是**碰巧**
撞见其中一项：DOMPurify 默认会把 `<markdown-accessiblity-table>` 这类自定义元素
整个 unwrap 掉（保留子节点、丢外层标签）。

**已知影响面（实测边界，不是全集）**：
- `markdown-accessiblity-table` 被 unwrap → 表格照常渲染。readit 不注册它的定义，
  它是个惰性挂点，损失是语义/可访问性钩子，不是视觉。
- `math-renderer` 被 unwrap → **只影响降级路径**。实测确认 MathJax 正常输出的是
  `mjx-container`，`math-renderer` 只在数学未加载时的 GitHub 形状回退里出现。
- 属性面**不受影响**：DOMPurify 默认 `ALLOW_DATA_ATTR`/`ALLOW_ARIA_ATTR` 为真，
  `data-line`（M4 滚动同步承重）与 `id` 在 WebKit 上从未失效——
  `browser/element/navigation.spec.ts:24-33` 有独立的实测记录佐证这一点。
- **不是安全面**：unwrap 保留内容、只丢标签，没有放宽任何东西。

**谁会撞上**：Safari/WebKit（无原生 `setHTML()`，`hasTrustedTypes` 为真 → 选中第 2 级）。
净效果是同一份文档在 Safari 与 Chrome 上 DOM 结构不同。

**怎么还**：给第 2 级的 DOMPurify 配置补 `ADD_TAGS`（或 `CUSTOM_ELEMENT_HANDLING`），
让两级的允许名单对着 Phase A 的输出**对齐**。但**不要只补这两个名字**——
那正是这个项目反复栽的坑（见下节）。要做的是把第 1 级那次「跑一遍完整语料、
`DOMParser` 解析出期望集合、逐元素逐属性 diff 到零差异」的诊断**在第 2 级重做一遍**。

**这次测量必须在真浏览器里做。** 控制端试过在 happy-dom 里测，**测量作废**：
阳性对照显示 `DOMPurify.sanitize('<script>b()</script>')` 在 happy-dom 下
**原样返回 `<script>`**，同时 `isSupported` 报 `true`——DOMPurify 在这个 DOM 实现下
遍历行为不正常，任何差集都是假的。（现有单元测试没有被它骗到：第 2 级在单元层
一直走 `DomPurifyLike` 端口注入桩，这个设计恰好挡住了这颗雷。**以后谁想把真
DOMPurify 接进单元测试，先读这一条。**）

**归属**：批次 8（Task 19 SPEC 同步那批，已在收拢清理项）。不紧急——不是安全面，
主路径无视觉破坏——但要在计划二收尾前落地，否则计划三会继承一个「两级消毒器
名单不一致且无人知道差在哪」的状态。

### ~~D2-18 组合期外部 `setValue()` 会静默丢弃用户刚提交的输入法文本~~ —— ✅ 已裁决：维持现状（用户，2026-08-11）

**批次 8 做了什么、没做什么**：SPEC.md §9.4 在 `mount()` 签名后补了一段明确措辞，

**来源：实测**（批次 7 评审，读 `codemirror.ts:53-77` 的 `applyDeferred`/`write` 逻辑
