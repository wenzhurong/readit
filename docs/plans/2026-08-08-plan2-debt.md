# 计划二的在案债务

计划一收尾时的完整欠账清单。每一条都**具名、带出处、可核验**——与
`packages/core/test/known-mismatches.json` 同一原则：债务的价值在于它是一份可读的清单，
不是一个静音开关。

出处标注三种：**实测**（有命令与输出）、**评审实测**（评审自己跑的探针）、
**推断**（从测量泛化，未单独验证——这类在本项目里已经错过四次，看到就当它可疑）。

## 一、三条「自选广度」的承重声明

全分支评审点名的一类风险：**声明的广度由做声明的人自己选定**。这条分支上它已经
造成四次「完整集」被后一轮推翻（`<template>` → `+script` → `+col` → `col 其实位置敏感`）。
下面三条同源，且**尚未被任何更宽的测量检验过**。

> **2026-08-09 更新：三条里的第一条已经用更宽的测量检验过了，结果是被推翻。**
> D2-1 的「带 height 就发扩展形式」在七种 `height` 形态里错了四种。
> 这是这一节的论点第五次被自己的样本证实——**推断的广度由做推断的人选定时，
> 它倾向于错**。剩下 D2-2 / D2-3 两条仍未检验，性质完全相同。

### ~~D2-1 `imageStyle` 的三声明形式源自 n=1~~ —— ✅ 已还清（2026-08-09，实测）

- **位置**：`packages/core/src/rules/rawshape.ts` 的 `imageStyle`
- **原判断**：带 `height` 属性的图片发
  `style="max-width: 100%; height: auto; max-height: <N>px;"`，
  不带的发 `style="max-width: 100%;"`。整个夹具集里**只有一个**实例支持扩展形式
  （`real-world/mermaid` 的 `<img height="150">`），对 46 个朴素实例；
  代码里标了三处 UNVERIFIED，但它们**静默走 height 分支**。
- **怎么还的**：八个单目的语料（`github-only/image-height-*` +
  `image-width-and-height`），每个一个 `<img>` 形态，
  2026-08-09 对活 oracle 抓取（`contents` + `Accept: application/vnd.github.html`，
  自仓 ref `c764d959`）。

#### 实测结论：**推断是错的，四处于七。**

| `height` | 语料 | GitHub 发的 `style` |
|---|---|---|
| 无 | `image-height-none` | `max-width: 100%;` |
| `150` | `image-height-numeric` | `max-width: 100%; height: auto; max-height: 150px;` |
| `50`（且有 `width`） | `image-width-and-height` | `max-width: 100%; height: auto; max-height: 50px;` |
| `50%` | `image-height-percent` | `max-width: 100%;` ❌ 原分支发 `max-height: 50%px;` |
| `10em` | `image-height-css-unit` | `max-width: 100%;` ❌ 原分支发 `max-height: 10empx;` |
| `0` | `image-height-zero` | `max-width: 100%;` ❌ 原分支发 `max-height: 0px;` |
| `abc` | `image-height-junk` | `max-width: 100%;` ❌ 原分支发 `max-height: abcpx;` |

**真正的判据是「正整数像素」，不是「有 height 属性」，也不是「值是数字」**
——`height="0"` 走朴素分支，这一条谁都没预测到，它才是把判据钉死在「正」而非
「数值」上的那个证据。三处 UNVERIFIED 里，只有 `width`+`height` 那一处
碰巧猜对了（`width` 不干扰，判据只看 `height`）。

四处错误全部产出**语法非法的 CSS**（`50%px` / `10empx` / `abcpx`），
且都发在原生 HTML 文档里——正是评审判定它风险/行数比最高的理由。

**附带定论**：`image-height-markdown` 证实 Markdown 图片语法**无法表达 height**
（GitHub 既不支持 kramdown/Pandoc 的 `{height=150}`，也不支持 `=150x`），
所以扩展形式从 `decorate.ts` 那侧不可达，它无条件发朴素形式是对的——
这是求证的结果，不是假设。

#### 仍未测量（现在**失败朝安全侧**，且已在代码注释里具名）

带空白的高度、前导零（`"0150"`）、小数、负数、超过 2^53 的值。
这些一律走朴素分支：那是 46 实例的多数分支，且永不产出非法 CSS。
它仍然是一个猜测，只是猜向了实测占优的一侧。另注：hast 会重写属性本身
（`height="0150"` 序列化回 `height="150"`），这类文档在轮到 `style` 之前
就已经与 GitHub 分叉了——那是序列化器的问题，不是 `imageStyle` 的。

- **代价**：语料 60 → 68，SPEC §13.3 上限由 60 上修至 70（见该处的修订说明）。
  八个新文件**全部匹配 oracle**，台账未增加条目（仍 12 条），语料 48/60 → 56/68。
- **出处**：全分支评审（架构）、修复轮 3 评审；本轮为实测还清

### D2-22 容器里两个宿主的锚点内联盒差 2px —— 计算样式看得见，像素比对看不见

**来源：实测**（2026-08-12，CI 的 noble 容器；本机 macOS 复现不出来）。

`hostile-isolation.spec.ts` 报出 4 处差异，全部由同一个元素的高度派生：

```
block-size        clean 18px      hostile 16px
height            clean 18px      hostile 16px
perspective-origin  clean 10px 9px  hostile 10px 8px
transform-origin    clean 10px 9px  hostile 10px 8px
```

20px 宽、18/16px 高的内联元素——形状对得上标题锚点里那个 octicon `<a>`。

  又是一次自选广度——这条分支为那个模式栽过九次。

两项加进去（`tabSize`、`textSizeAdjust`，见 `browser/support/visual.ts` 的注释）。
全枚举那一版的价值已经兑现——它逼出了那两项。

**怎么还**：在容器里量一次两个宿主对该 `<a>` 解析到的实际字体与 ascent/descent。

### D2-24 壳的自动化层有一类结构性盲区：应用启动级缺陷

**来源：实测**（2026-08-14，C6 的真机探针连撞两处）。

Phase C 的自动化只有两层：Rust 单测（`cargo test`）与 happy-dom 下的前端单测。
一次真 `.app` 运行当场暴露两个**这两层在结构上都够不到**的既有缺陷，
两个都会让应用第一次启动就是坏的：

1. **`rewriteLocalResources` 用了非法 CSS 选择器 `[src]img`**（类型选择器必须在复合选择器最前）。
   实测：Chromium 与 WebKit 都抛 `SyntaxError`，而 **happy-dom 静默接受并正常匹配**。
   也就是说这个把本地图片改写成 `readit://` 的函数在真实应用里第一次调用就抛，
   **相对图片根本不会显示**——而手工清单第 1 项正是「相对图片可见」。C1 的单测全绿。
2. **缺 capability 文件**：UI 只显示 `Command plugin:event|listen not allowed by ACL`。

两个都已修，且第一个补了**真浏览器合同**（`browser/element/shell-links.spec.ts:42`，
控制端注入验证过它在两个引擎上都红）。留下的债务不是这两个 bug，是**盲区的形状**：

- `shell/vitest.config.ts` 的 environment 是 `happy-dom`，它对选择器、CSS、
  以及一切「真引擎会拒绝而它接受」的东西都比真浏览器宽松。
- 目前只有 `shell-links` 与 `shell-find-shortcut` 两条 spec 把壳前端放进了真浏览器；
  `resources.ts` / `updates.ts` / `watch-reload.ts` / `main.ts` 的其余逻辑仍只有 happy-dom。

**怎么还**：把壳前端里「会跟真引擎打交道」的部分逐一移进真浏览器合同——
判据不是"覆盖率"，是"这段代码有没有依赖引擎的严格性"。选择器、CSS、DOM API 的
边缘行为都算。**不要靠加 happy-dom 测试来还这条债**，那正是没抓住它的那一层。

**2026-08-17 补记：盲区还有第二层，比上面这层更难对付。**

M6 真机验收发现 `classDef` 的 `opacity` 绕过了 mermaid 的图层护栏（护栏只摘行内
声明，而 classDef 编译成注入 SVG 的 `<style>` 规则）。查它的时候量出一件事：

| 层 | 前提（标签计算 opacity = 0.3） | 症状（标签画到未变换的原点） |
|---|---|---|
| happy-dom | ❌ 表达不了（`<style>` 内容被整个丢弃） | ❌ |
| Playwright 无头 WebKit | ✅ 忠实复现 | **❌ 不复现** |
| 真 WKWebView（`.app`） | ✅ | ✅ |

也就是说**真浏览器合同这一层也有它够不到的东西**：合成（compositing）行为在无头与
真机之间不一致，WebKit bug 23113 这类合成缺陷只在真机上显形。上面那条债的还法
（「移进真浏览器合同」）对这一类**不够**。

可行的办法是**把门开在前提上而不是症状上**——`browser/element/mermaid.spec.ts` 现在
断言的是「foreignObject 里没有任何一层带非中性的 opacity/transform/filter」，
这个在无头 WebKit 上量得到，且它成立就意味着 23113 的触发条件不成立。
这个思路可以推广：**当症状只在真机显形时，找一个自动化层量得到的、蕴含症状不发生的
前提去守它。**

### D2-25 `mailto:` 被外链网关拒绝 —— 已决定，但值得复看

### D2-29 文件监听的沉降只有 80ms，非原子写入仍可能被读到中间态

**来源：实测**（2026-08-17 M6 手工验收第 4 项的附加探测）。

Rust 侧是裸 `notify::recommended_watcher`（`shell/src-tauri/src/watcher.rs:18`），
**没有 debouncer**；沉降全靠前端 `shell/src/watch-reload.ts:14` 的 `delayMs = 80`。
用一个人工的 600ms 半写入窗口（截断 → 写前半段 → 停 0.6s → 写后半段）探测，readit
**会短暂显示残缺内容**，写入完成后自行纠正。

**这不构成第 4 项失败**：清单点名的两种保存方式（临时文件 + rename、普通原地写入）
都通过了，600ms 是人工条件，真实编辑器不这么写。

**也基本不可修**。POSIX 没有任何办法让读者知道一个不配合的写者写完了——「原子保存」
（临时文件 + rename）存在的理由正是把这件事变成一次原子的目录操作。可选的收紧手段
都只是把窗口挪窄：把 80ms 调大、或加一个「size + mtime 稳定 N 毫秒才读」的沉降循环。
**当前决定是不动**，把它记成已知边界。

**什么时候该重新考虑**：如果出现「用户报告偶尔看到半截文档」的真实反馈，或者出现
明确会慢写的场景（网络盘、同步盘、大文件由外部进程增量生成）。届时优先做沉降循环
而不是单纯加大常数——加大常数是把竞态记成一个数字，这个项目已经因此栽过两次。

### D2-30 为 Windows 改了共享库：`\` → `/` 的归一化对所有平台生效

**来源：实测**（2026-08-18，控制端复核 `agent/windows-shell`）。

`packages/element/src/navigate.ts` 的 `normalizeWindowsPath()` 无条件对 href 与 baseUrl
跑 `replaceAll('\\', '/')`，而这是**共享库、所有平台都走的路径**。POSIX 上反斜杠是合法
文件名字符，实测：

```
/Users/mac/lit\eral.md  →  /Users/mac/lit/eral.md
```

CommonMark 里 `\e` 不是可转义序列，所以 `[x](lit\eral.md)` 的目标就是字面的
`lit\eral.md`，GitHub 会链到那个文件；readit 现在会导航到 `lit/eral.md`。

**这正是本项目 ≥10 次记录的那个失效模式的形状**：为一个平台做的修改，广度由做修改的人
选定，然后无条件铺开。

**为什么没有在复核时顺手改掉**：壳侧其实已经在边界归一化了
（`shell/src/document-path.ts`，`main.ts` 传给 `mount()` 的 `baseUrl` 已是斜杠形式）。
元素之所以还需要懂 Windows，只是因为壳对 UNC **保留了反斜杠**
（`\\?\UNC\srv\share\a.md` → `\\srv\share\a.md`），把收尾留给了元素。
控制端在 macOS 上无法验证改动后的 Windows 行为，而 Rust/TS 两侧的测试都钉着当前形状，
贸然改会在无法复核的平台上制造回归。

**怎么还**：让壳把 UNC 也一次归一化到底（`\\?\UNC\srv\share` → `//srv/share`），
然后把 `normalizeWindowsPath()` 连同 `classifyHref()` 里那条 `\\` 分支一起从
`@readit/element` 删掉——共享库回到平台中立。**必须由能在 Windows 上实测的人做**，
且要保留 `packages/element/test/navigate.test.ts` 现有的两条 Windows 用例作为回归证据。

**附带观察**：`classifyHref()` 新增的 `if (href.startsWith('\\')) return 'relative'`
在行为上是**无操作**——任何以 `\` 开头的串本来就既不匹配 `//` 也不匹配
`SCHEME_RE`（它要求首字符是字母），原本就会落到末尾的 `return 'relative'`。
留着无害，但它不是这条债务的成因。

### D2-31 壳的 `breaks: true` 对约一半的真实文档是误断 —— ⏸️ 可选延后项

**来源：实测**（2026-08-18，在用户的 `~/Desktop/egonex` 上量）。

2026-08-18 给引擎加了 `breaks` 选项，桌面壳置 `true`（软换行发 `<br>`），理由与裁决见
SPEC §9.4。那条裁决是对的，但它有一个当时没量、事后量出来的代价。

`breaks: true` 把**段落内每一个换行**都变成真换行，它**无法区分**作者是「想分行」还是
「只是把长句折了一下」。在 271 份有段落内软换行的真实文档上实测：

| | 处数 |
|---|---|
| 像「一行一句」——开关是对的 | **2716** |
| 像「句中折行」——开关会断错 | **2541** |

判据是「上一行结不结束在句尾标点、且够不够长」，是启发式不是精确判定，但量级可信。
形态上大致分成两类：中文写的报告/清单基本是一行一句（开关纯收益）；英文写的设计评审、
CODEMAP、spec 里有大量按 80 列硬折的段落（开关会把句子断在中间）。

**为什么不是缺陷**：这正是 Cursor / VS Code 预览 / Obsidian 一直以来的行为，用户是在
那个观感下写的这些文档。壳选它是有意的产品裁决。

**为什么仍要记**：`shell/src/main.ts` 里只看得到「已决定」，看不到「代价是一半文档」。
这个项目最贵的一课就是限定词在转录中丢失。

**⏸️ 用户 2026-08-18 明确定为可选延后项，当前不动。**

**怎么还（三选一，都不急）**：

- **A 维持现状**：中文报告类修好了，英文硬折行类会断碎。
- **B 壳改回 `false`**：回到 08-18 之前，需要分行的文档自己加行尾反斜杠（可移植，
  在 GitHub 上也对），但历史文档要逐份改。
- **C 让 `readit-breaks` frontmatter 在壳里生效**：逐文档可控，最干净。**卡在一个
  公开 API 缺口上**——壳换文档走 `handle.setValue()` 而不是重挂（重挂会清掉元素的
  历史栈，前进/后退就没了），而 `breaks` 只在挂载期读一次。要做得先给 `MountHandle`
  加一个改选项的入口，那是公开 API 扩张，值得单独一轮而不是夹在别的改动里顺手加。

### D2-32 macOS 的 Apple Event 退出仍绕过未保存修改的提示

⌘Q 与菜单 Quit 已经在 2026-08-18 修好（自建菜单项 → `leave::request_exit_from_menu`），
但**注销、关机、`osascript -e 'tell application "readit" to quit'`** 这三条走的是 AppKit 的
`terminate:`，和原来那个预定义 Quit 是同一条路径。tao 0.35.3 没有实现
`applicationShouldTerminate:`，`RunEvent::ExitRequested` 不会发出，因此在应用层**没有
拦截点**——脏文档会被静默丢弃。

**为什么不现在修**：需要自己往 NSApplication 的 delegate 上挂 `applicationShouldTerminate:`
（unsafe objc，且要和 tao 自己的 delegate 共存），或者等上游支持。相对 ⌘Q 这条日常路径，
触发条件少得多。

**风险已明写在 SPEC §10.1**，不要把「退出保护」的覆盖面说得比这更宽。

## 附：本项目反复出现的一种失效模式

值得写进计划二的工作方式，因为它在计划一里出现了**至少五次**：

> **把「实测到的」当成「从实测泛化出来的」来用。**

已发生的实例：
- Task 11 —— 控制端把自己的推断当「计划原文」传给评审，评审据此产出了严谨但前提错误的发现
- Task 15 —— `CORE_SCHEMA` 的泛化
- Task 26 —— D-$5 的偏离夹具没有断言任何 GitHub 侧的值
- Task 33 —— SPEC 说「外部链接与全部自动链接」得 `nofollow`，实测 `mailto:` **三种形式都不得 `rel`**；照散文实现会**引入**一处偏离
- Task 34 —— Task 24 报告把 `\,` → `,` 写成缺陷症状，而 GitHub 自己的输出里也是 `,`
- 修复轮 1/3/5 —— 「完整触发集」被推翻三次（`template` → `+script` → `+col` → `col 其实位置敏感`）
- 注释声称的测量广度超过其测试，**五次，每次都在上一次的修复里**
- 2026-08-18 M6 第 7 项 —— `document.rs` 把 CRLF **直接喂给** `save_document` 并断言字节
  原样返回，证明的是写入层；而验收清单要求的是「磁盘字节精确保留 CRLF」这条端到端。
  CRLF 出现在测试源码里，看起来已覆盖，实际端到端是断的
- 2026-08-18 M6 第 7 项 —— `leave.rs` 断言 `intercept()` 这个纯状态机的返回值，从不断言
  ⌘Q 时有人调用它；SPEC 却写着「CloseRequested/ExitRequested 都经过前端脏状态裁决」。
  执行报告本身是诚实的（明写「系统级关闭/退出流程尚未真机证明」），**是那条保留在写进
  SPEC 时被抹平成了无条件陈述**
- 2026-08-18 `shell_menu.rs` —— 防漂移守卫用 `include_str!` 读整个文件（含测试模块自身），
  断言里的针就是字面量，每条 `contains` 都被自己满足。**守卫恒为真，零覆盖**
